The model drafts.
Code decides if it ships.

Repurpose turns one source document into content for every channel a client publishes on — and refuses to hand any of it over until automated checks have signed off. This is the run that matters: 

$ repurpose samples/source.md --profile profiles/example.yaml --dry-run

[FAIL] linkedin_post              436 chars, 2 attempt(s)
        [FAIL] claims_grounded: '47%' does not appear in the source material
        [FAIL] banned_phrases: contains banned phrase 'it's important to note'
        [FAIL] required: missing required element 'northwind.example/report'
[WARN] cross-channel: shares 8+ words verbatim with 'linkedin_post'

Review failed — nothing here is ready to publish.
$ echo $?
1

The model wrote a clean, confident paragraph claiming a 47% improvement. That number is nowhere in the source document. The gate caught it, tried one rewrite, caught it again, and exited non-zero.

The problem

Fluency is not the hard part anymore

Anyone can prompt a model into a passable LinkedIn post. Clients don't stop paying because the writing is bad — they stop because somewhere in the batch is a statistic nobody can source, or because the tenth post this month opens with the same three sentences as the ninth.

Those failures are cheap to make and expensive to find by hand. So this pipeline treats them as build failures. Non-zero exit, no publish, and a scorecard naming exactly what broke.

What the gate enforces

Six checks, run before a human sees anything

CheckSeverityWhat it catches
claims_grounded Fail Any number in the draft absent from the source — the fabricated-statistic failure
banned_phrases Fail House-style violations and stock machine register
length Fail Platform ceilings and editorial minimums
required Fail Missing link, call to action, disclosure, or legal line
readability Warn Drift above the audience's reading level
duplication Warn Verbatim runs reused across two channels

Failures block. Warnings inform. The distinction is the whole design: a gate that blocks on everything gets switched off within a week.

The loop

Draft, review, repair, decide

  1. Draft

    One prompt per channel, built from the client's profile — voice, audience, brief, and the constraints the gate will later enforce. The model is told the rules before it is judged against them.

  2. Review

    Every draft runs through the gate. No API calls, no second model grading the first — pure functions over the draft, the source, and the rules.

  3. Repair

    A failed draft is handed its own scorecard and asked to fix precisely those issues. Most runs self-correct here.

  4. Decide

    Still failing after the retry budget? Non-zero exit and a scorecard. The pipeline would rather deliver nothing than deliver something wrong.

Decisions worth defending

Three choices that carry the design

The gate has no model dependency

qa.py imports nothing from the LLM layer. Every check is a pure function over (draft, source, rules), which is what makes the rules testable and what stops the reviewer inheriting the writer's blind spots.

Client rules extend the defaults, never replace them

Adding one client-specific banned phrase used to silently switch off the nine built-in ones. That was a real bug, caught by a test, and the fix is the more important half: config that fails safe rather than fails quiet.

The offline stub fails on purpose

--dry-run swaps in a stub that fabricates a statistic and reuses source sentences. A demo mode that always passes proves nothing; this one shows the gate working, with no API key and no network.

Verification

Twenty tests, none of them decorative

The suite covers number normalisation ($1,200,000 against 1200000), list markers that look like numeric claims, the repair loop firing exactly once, the pipeline giving up after its retry budget, and the CLI's non-zero exit. It runs without a network connection.
